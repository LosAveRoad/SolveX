# ADR-0015：评审、修复、论文以提交工具结束

- 状态：Accepted
- 日期：2026-11-20
- 关联：ADR-0013（评审循环）、ADR-0014（交付物门禁、复现门禁、论文门禁）、`docs/benchmark.md`

## 背景

以前判断一次调用「做完了」，看的是模型最后一条回复的文字，或者事后检查文件在不在。r6 里有三类失败都被当成了完成：

- **评审**：6 次评审里 2 次以空回复结束。Model 1 只读了 3 个文件，追问结论后直接判 SATISFIED；Model 3 第 3 轮空回复，修复拿到的是空意见。r5 里评审写了 12 KB，却漏了结论行。
- **修复**：Model 3 的 3 次修复一个文件都没改，照样通过复现门禁（代码没变，重跑结果当然一致）。错误的引擎输出（med_place 0、Jerry Rice p_win 1.0）就这样进了论文。
- **论文**：写完引言和 Model 1 就以空回复结束；摘要停在占位符 `PHOLDER`；题面要求的备忘录没写。

ADR-0014 的补救办法是事后补问：REPORT_FOLLOWUP、VERDICT_FOLLOWUP，以及论文门禁接着催写。这些办法都要猜回复文字的长度和格式，每补问一次就要多发一条消息。

## 决策

1. **显式完成工具**。`RunRequest.submit` 携带一个提交工具（名字、描述、JSON Schema、`check`），运行时把它注册成这一次调用的工具，同时进 `tools`、`customTools` 和提示词里的工具清单。只有 `check` 接受了提交，这次调用才算交付（`RunResult.submitted`）。这是常见做法：ReAct 的 `Finish[answer]`、SWE-agent 的 `submit`、OpenHands 的 `finish`、Inspect 的 `basic_agent` + `submit()` 都是这样。
2. **`check` 当场把关**。处理函数做确定性检查，不合格就把原因作为工具错误原样回给模型，模型在同一轮里补齐后再提交，不用等调用结束再补发一条消息。

   | 阶段 | 工具 | 参数 | check |
   |---|---|---|---|
   | 评审 | `submit_review` | `verdict`、`review` | 结论只能是 SATISFIED 或 NEEDS_REVISION；正文去掉结论行后不少于 400 字；NEEDS_REVISION 必须带 Fix Instructions |
   | 评审修复、复现修复 | `submit_fix` | `summary` | 修复说明不少于 40 字；可以选择不改（评审也会误判），在说明里写理由即可；评审修复如果改了文件，就必须同时更新 `results_summary.md`（复审读的是它）。每次修复改了哪些文件（按修复请求发出时的哈希指纹比对）都会写进事件日志 |
   | P4 | `submit_paper` | 题面要求备忘录时：`memo`（必填）、`memo_title` | 跑论文完整性门禁（每个模型一节、真实摘要、结论、无占位符、`\end{document}`）；备忘录不少于 1200 字、无占位符。接受后 SolveX 把备忘录写成 `memo.tex`，插到 `\end{document}` 之前；论文里已经有备忘录一节时不重复插入 |

3. **没提交就在同一会话里催**。调用结束时还没有被接受的提交，就发一条催促消息，列出仍缺的部分（`<call>-submit-<k>`，评审 2 次、修复 2 次、P4 5 次）。工具调用不能保证模型一定会提交，所以催促仍然需要，但催促条件变成了「没有被接受的提交」，不再需要猜文字。
4. **评审只认提交**。落盘的评审全文 = 提交的 `review` + 结论行；REPORT_FOLLOWUP 和 VERDICT_FOLLOWUP 删除。保留一个兜底，r7 验证后再删：始终没有被接受的提交时，从各次回复里取最长的评审和结论行；没有结论但列了问题，按 NEEDS_REVISION 处理。
5. **修复基线落盘**。修复请求发出时的指纹写在 `.solvex/journal/<会话>.<call>.baseline.json`。中断后续跑时沿用这份基线，不会把崩溃前已经做的改动当成原样。实现方选择不改时，不再补一轮摘要。

   最初的设计是「修复必须改动文件」（r6 里 Model 3 的 3 次修复一个文件都没改）。后来放弃了：这条规则不允许实现方反驳评审，评审误判时只能硬改，可能把正确的结果改坏；而加一行注释就能通过，它也拦不住敷衍的改动。现在改为允许不改，但每次修复改了什么都可查：修复后有复审，复审时一眼能看出没改；第 3 轮修复后不再复审，r7 跑完后人工抽查。
6. **续跑**。提交结果写在 toolResult 的 `details.solvexSubmit` 里，Pi 会把它写进会话 JSONL。回放已完成的调用、续跑中断的调用时，都从日志里恢复 `submitted`。
7. **占位符检查**并入论文门禁：只认全大写的 `PHOLDER`、`PLACEHOLDER`、`TODO`、`TBD` 和 `Lorem ipsum`，不看 LaTeX 注释（r5 正文里有普通单词 "placeholder"）。

## 不做的

- **初始实现不加提交工具**。交付物门禁（摘要、`run.py`、`results.json`）加上复现门禁已经够用，实现的自评结论也照旧读取。
- **不给反驳单独设流程**（比如把反驳理由转给下一轮评审裁决）。复审本来就是从当前状态重新评审，不需要额外的流程。
- **复现检查不放进 `submit_fix` 的 check**。`run.py` 可能要跑几分钟，放进 check 会让模型反复提交、空耗轮次；复现门禁仍在修复之后由编排层单独跑。
- **接受提交后不强行中止会话**。工具返回「已接受，结束本轮」，由模型自己收尾。

## 影响

- `SolveXFlow`：评审、修复、复现修复、P4 改为「调用 → 没提交就催」；`CONTINUE_NUDGES` 只剩 P1 和实现两项。
- `FakeAgentRunner` 会按工具名模拟提交（评审的结论和正文取自回复文字），修复调用会真的改动文件。
- 真实模型冒烟测试：`bench/probe/submit_smoke.ts`，结果见 `docs/benchmark.md`。

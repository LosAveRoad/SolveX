# ADR-0014：规划节点建共享数据集、复现门禁、评审可跑代码、放宽预算

- 状态：Accepted
- 日期：2026-11-20
- 关联：ADR-0008（离线执行策略）、ADR-0009（结果契约）、ADR-0011（工具清单代码发现）、ADR-0013（评审循环）、`docs/benchmark.md`

## 背景（r3–r5 评审意见与运行数据）

- **规划者没看过数据**。P1 的运行时策略写着"不要浏览文件系统、第一步写计划、写完即停"（ADR-0008 为解决幽灵工具死循环所加），基准题面还要求"第一步必须 write"。计划因此常定下数据支撑不了的目标（复现率 ≥0.85、PPC、LOO），实现做不到，评审判不通过。
- **各模型重复犯同类数据错误**：r3 融表后只剩 335/3,335 行；r5 把 0 分周当成有成绩、标反了第 28–34 季的规则；r3/r4 舞伴名带集数注释、行业大小写重复；r5 把退赛行混进估计值。每个模型各自解析原始 CSV。
- **最常见的评审问题是"数字对不上产物"**：摘要里的数字在文件里找不到、文件是过期的、脚本跑不出交付的结果（r5 模型 3 第 3 轮 8 个问题里大半如此；r5 论文头条 86.8% 实为别的指标）。
- **评审只能读，不能验证**：只读工具下评审只能"读出怀疑"，无法重算。
- **预算不够**：r4、r5 实现会话 3/3 每轮撞 30 轮上限。

## 决策

1. **P1 拥有完整权限，先看数据、建共享数据集，再写计划**（原第 4、5 两项合并）。新策略 `PLANNING_POLICY` 保留 ADR-0008/0011 的网络与工具规则（以发现的清单为准、不模拟缺失工具、不联网，且不出现具体工具名），去掉"先写计划、写完即停、不许看数据"。三步：检查数据 → 在 `01_modeling/shared_data/` 建共享数据集（`prep_data.py`、清洗后的 CSV、`data_dictionary.md`、`checks.md`）→ 基于它写计划，验证目标须为数据所能支撑。P1 写完计划却没建数据集时，在同一规划会话追问一次。基准题面里"第一步必须 write、写完即停、不许跑 bash"的 P1 约束随之删除。
2. **共享数据集与 master_plan 在 P1 之后只读**。写拦截只覆盖 write/edit 工具，bash 与 Python 执行能写任何地方，所以只读靠事后还原：P1 结束后对两者拍一次快照，每个实现节点、修复、复现修复、评审结束后都按这份快照还原（并告警）。只拍一次是为了避免并行评审之间的竞态（后拍的快照会把别人的改动当成原样——旧 `withMasterPlanGuard` 就有这个问题）。
3. **实现提示附上共享数据集说明**（`sharedDataNote`），要求直接加载、不要重新解析原始文件。
4. **结果契约 + 复现门禁**。`RESULTS_CONTRACT` 增加：入口脚本 `run.py`，从模型目录运行能确定性地重新生成全部产物；`run.py` 写出 `results.json`（全部标题数字）；摘要里的数字只能抄自 `results.json`。编排层在实现结束后、每轮评审修复后重跑 `python3 run.py`（异步，超时 30 分钟），比对重新生成的 `results.json`；崩溃、缺文件或数字不一致，就把结果（stderr 或差异清单）发回该模型的实现会话（`repro-<阶段>-<n>`），最多 2 次，仍失败则告警放行。门禁是纯代码，不经过模型。
5. **评审可以跑代码**：评审工具加 `bash`、`python_execute`，运行时说明覆盖逐字资产 review.md 里"不写也不跑代码"一句；草稿写在 `.solvex/scratch/`。评审前对本模型目录拍快照、评审后还原，共享数据集与 master_plan 按第 2 条还原——评审能验证，但改不了实现。
6. **预算**：轮次上限建模 25→60、编程 30→90、评审 20→50、写作 40→100；基准思考等级 medium→xhigh（网关映射为 max）。模型仍为 GLM 5.3 Flash。产品的默认思考等级不变（WebUI 可按阶段配置）。

7. **交付物门禁：提前停下就在同一会话里催它接着做**。r6 首次尝试实测：GLM 5.3 Flash 在多步任务里会说完"接下来我要重写 prep_data.py"就结束本轮、不调用工具——P1 计划调用在第 16 轮、重试在第 4 轮停下（预算 60 轮），两次都没写出计划，流水线以 MasterPlanError 中止。现在 P1（master_plan + 共享数据集）、实现（results_summary.md、run.py、results.json）、P4（main.tex）结束时都检查交付物，缺什么就把清单发回同一会话（`<调用>-continue-<k>`）让它接着做，最多 P1 4 次、实现 3 次、P4 3 次；取代原来的单次 "URGENT" 计划重试与摘要补写。
8. **基准脚本自动续跑**：r6 首次尝试另遇一次上游中断（SSL EOF 持续超过 SDK 约 2 分钟重试窗口，P1 在第 329 秒失败）。`bench/run.ts` 遇到模型调用失败时等 60 s，在同一工作区用产品的日志续跑重新执行流水线，最多 3 次，记入 `metrics.resumes`。
9. **评审必须有书面正文**（已由 ADR-0015 的 `submit_review` 取代）。r6 正式运行实测：6 次评审里 2 次在调完工具后以空回复结束（`stopReason: stop`、内容为空、输出 21 / 93 token）。原有的结论追问只要一行结论：Model 1 只读了 3 个文件、空回复后被追问，直接答 SATISFIED，等于没评审就放行；Model 3 第 3 轮空回复，修复拿到空意见。现在评审最终回复去掉结论行后不足 `MIN_REVIEW_CHARS = 400` 字，就在同一评审会话里发 `REPORT_FOLLOWUP`（调用 `report`）：调查结果都在上下文里，不重做调查，直接写出书面评审并以结论行结尾；结论只从书面评审里取，之后才走原有的结论追问。

10. **P4 论文完整性门禁**（ADR-0015 起改为在 `submit_paper` 的检查里执行）。r6 实测：写作 Agent 先花 19 轮核对产物数字，写完引言和 Model 1 一节就以空回复结束；旧门禁只看 `main.tex` 是否存在，半篇论文被当成交付。`paperGaps`（`gates/paperGate.ts`，纯函数）检查每个计划模型各有一个标题含 "Model k" 的 `\section`、有 Conclusion、有不少于 300 字的摘要（r6 续跑后的论文摘要仍是占位符 `PHOLDER`）、有 `\end{document}`，题面提到 memo 时还要有备忘录一节；缺的部分逐项交给交付物门禁，在同一写作会话里催它接着写（P4 催促上限 3→5，论文本来就分多次写入）。r5 的论文没有备忘录，这个门禁也会拦下。
11. **长上下文下降低思考档，不提前压缩**（同日修订，取代初版的「128K 就压缩」）。初版根据 r6 现象（Model 3 实现会话到 175–180K 后修复只说不做、出现乱码路径）判断为上下文长度导致退化，把压缩提前到 128K。随后用上下文探针（`bench/probe/`）单独验证，结论不同：
   - **乱码路径与长度无关**：r6 全部工具调用里，0–25K 与 50–75K 的路径出错率都约 6%，175K 以上为 0；短上下文下中文路径与 ASCII 路径各拼 60 条，0 错。
   - **重放真实会话**（r6 Model 3 修复前的历史截到 30K–177K，发同一条修复意见）：30K–126K 下 max / high 共 30/30 正常调用工具；177K 下 high 9/9 正常，max 只有 5/9（3 次只说不做，与 r6 一致；1 次路径错）。
   - **大海捞针**：81K、157K、300K、583K 均 5/5（449K 一次 0/5，重跑两次均 5/5）。上游实际接受 58 万 token。
   退化来自「长上下文 × 最高思考档」叠加。现在：会话上下文超过 `THINKING_DOWNGRADE_AT = 150K` 时把 xhigh 降到 high（新调用发进已有长会话时一开始就用 high，会话中途越过阈值时切一次）；压缩默认沿用 Pi（窗口 − 16K），`compactAtTokens` 保留为可选项；基准模型窗口改为 524288（网关报告 1M）。

## 取舍

- 单轮 token 与墙钟会显著上升（用户明确不在乎 token 成本）。复现门禁每次重跑 `run.py`，模型脚本慢时最多 30 分钟；续跑时实现调用虽然回放，门禁仍会重跑一次。
- 复现门禁在模型目录原地重跑：跑通后产物与代码一致（这是目的），但交付时的旧数字会被覆盖。
- 评审对其它模型目录的改动不在还原范围内（每个评审只守自己的模型目录，避免并行评审互相还原对方合法的修复）。
- 基准题面再次变化（删除 P1 的"先写、即停"约束），r6 起与 r0–r5 输入不完全一致。

## 验证

- `test/gates/reproduce.test.ts`：缺文件 / 非法 JSON / 一致通过 / 过期数字列出差异 / 崩溃带回 stderr / 超时 / 数值容差；文件快照还原。
- `test/flow/pipeline.test.ts`：P1 未建数据集时同会话追问、IMPL 提示附数据集说明；实现改共享数据集被还原；复现失败发回实现会话、修好通过、持续失败修 2 次后告警；评审跑代码的改动被还原、草稿保留、并行评审下 master_plan 正确还原。
- `test/flow/pipeline.test.ts`（交付物门禁）：P1 连续两次提前停下后第 3 次交齐、IMPL 缺 run.py/results.json 被催；P1 催满仍无计划 → MasterPlanError；P4 缺论文催 3 次后如实失败。
- `test/flow/pipeline.test.ts`（书面评审）：空回复、只有结论行的评审在同一评审会话被要求补写；结论与修复意见取自补写的评审。
- `test/gates/paperGate.test.ts`、`test/flow/pipeline.test.ts`（论文门禁）：r6 的半篇论文列出 4 处缺口；P4 只写了 Model 1 就被催着写完；r3 的完整论文通过、r5 缺备忘录被拦下。
- `test/pi/PiAgentRunner.test.ts`：xhigh 在 150K 以上降到 high（会话中途切一次；发进 175K 长会话的新调用一开始就是 high）；压缩默认不覆盖，设定阈值时按窗口换算。
- `bench/probe/context_probe.py`：E1 真实会话重放、E2 大海捞针、E3 中文路径（结果在 `bench/results/context-probe/`）。
- 既有测试中 FakeAgentRunner 的实现产物带 `run.py` + `results.json`，全部流程测试真实执行 `python3 run.py` 通过门禁。
